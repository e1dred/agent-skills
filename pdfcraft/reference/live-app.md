# PdfCraft reference: the live app (control channel)

Part of the pdfcraft skill. The short front page is `../SKILL.md`. Verified 2026-11-04 on **PdfCraft 0.18.2**, with the
app running on a private headless display (see "Running the app where the user cannot see it").

## Connecting

- Start: `pdfcraft --control FILE [file.pdf]` writes a random token to FILE (keep it in a private folder) and listens
  on loopback. Drive it with `pdfcraft-cli ui --control FILE <method> key=value …`.
- Methods (the list comes back in the error for an unknown method): `state`, `inspect`, `click`, `focus`, `resize`,
  `move`, `drag`, `type`, `key`, `command`, `commands`, `set`, `open`, `screenshot`, `quit`.
  - `state`: JSON of the window: `active` document (page, fit, layout, zoom, selection, find), `documents`, `dialog`,
    `notice`, `theme`, panels, `quick_tool`, `pending_opens`, `window`. `inspect [query=TEXT]`: widgets with ids, roles,
    labels and rects (176 on the start screen).
  - `command id=<ui id>` runs one of the **213 UI command ids** listed by `commands` (id, label, menu, shortcut, enabled).
    These are not the 189 engine tools; headless, the same registry is `command_list`/`command_run`.
  - `open path=/abs/file.pdf` opens a file **without a file chooser** — use it instead of `file.open`.
  - `set key=theme value=light|dark|system` (lowercase). `key key=F modifiers=ctrl` (egui key names; `Ctrl+F` is
    refused as a key name). `click id=<widget id>` or `x= y=` — a `label=` must match exactly; get ids from
    `inspect query=Find`. `drag from=[x,y] to=[x,y]` (points), `resize width= height=` (320–8192), `type text=` needs a
    focused field. `screenshot --out x.png`.
- **Check `state.active` first.** With no active document (`active: null`, e.g. after tabs were closed) every
  command answers success and changes nothing; an earlier sweep lost 170 results this way. Re-open with `open path=`.
- **Never send the chooser commands in an unattended run:** they open the desktop's native file dialog, which appears on
  the user's real screen even when the app runs on a hidden display, and a pending dialog makes later `file.*`/`create.*`
  commands answer "Another file dialog is still open". Chooser commands: `create.file`, `file.open`, `file.open_recent`, `file.pin_folder`, `form.merge_data`, `measure.export`, `ocr.recognize_batch`, `create.multiple`, `create.multiple_separate`, `create.images`, `file.save_as`, `file.properties`, `file.word_count`, `export.image`, `optimize.reduce`, `optimize.advanced`, `export.text`, `export.docx`, `export.pptx`, `export.html`, `export.rtf`, `export.all_images`, `protect.password`, `protect.properties`, `comment.import`, `comment.export`, `form.import_data`, `form.export_data`, `edit.attach`, `edit.image`, `page.insert`, `page.replace`. Treat any other command that reads or writes a file you did not name as one of them, and check `state.pending_opens` after each run.
- Settings are saved to the app's config (theme, recent files, last views): run test instances with their own `HOME`/XDG folders.

## Running the app where the user cannot see it

GNOME on Wayland gives scripts no way to put a window on another workspace. Instead run a private compositor and start
the app on its X display (the Wayland socket alone does not draw frames, so screenshots time out):

```
setsid -f env -u DISPLAY dbus-run-session -- mutter --headless --wayland --wayland-display=wayland-private --virtual-monitor 1920x1080 >mutter.log 2>&1 </dev/null
# mutter.log: "Using public X11 display :N"; the Xauthority file is the newest /run/user/$UID/.mutter-Xwaylandauth.*
# give the app the private compositor's own session bus, so file dialogs cannot reach the user's desktop portal:
BUS=$(tr '\0' '\n' < /proc/<mutter pid>/environ | sed -n 's/^DBUS_SESSION_BUS_ADDRESS=//p')
env -u WAYLAND_DISPLAY DISPLAY=:N XAUTHORITY=<file> DBUS_SESSION_BUS_ADDRESS=$BUS HOME=<test home> XDG_CONFIG_HOME=… XDG_DATA_HOME=… XDG_CACHE_HOME=… pdfcraft --control <file> test.pdf
```

`screenshot` and every other method work there. **Use the private bus:** with the user's session bus, any native file
chooser the app requests opens on the user's real screen (it comes from the desktop portal) even though the window is
hidden. On the private bus (verified with FilmCraft's `graphics.template.install`, which answers `{dialog:"open"}`)
nothing appeared on the user's screen and no picker showed on the hidden display either. Keep the chooser rule above anyway.
